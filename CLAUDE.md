## Project
Python orchestration layer, simulation engine, and Shiny web interface for the OSMOSE marine ecosystem simulator. Provides dual engine backends: a pure-Python engine (NumPy/Numba, full Java parity — 14/14 EEC, 8/8 Bay of Biscay) and the original Java engine (via subprocess). Python handles config I/O, execution, output reading, calibration, and visualization.

## Commands
- **Run tests:** `.venv/bin/python -m pytest`
- **Run single test:** `.venv/bin/python -m pytest tests/test_schema.py::test_name -v`
- **Run app:** `.venv/bin/shiny run app.py --host 0.0.0.0 --port 8000`
- **Lint:** `.venv/bin/ruff check osmose/ ui/ tests/`
- **Format:** `.venv/bin/ruff format osmose/ ui/ tests/`

## Architecture
Schema-driven: every OSMOSE parameter is defined once as an `OsmoseField` in `osmose/schema/`. The UI auto-generates forms from schema metadata. Adding a parameter = adding one field to the schema.

```
osmose/          # Core library (usable without Shiny)
  engine/        # Python simulation engine (44 files, ~11.5k LOC)
    simulate.py  # Main simulation loop
    processes/   # Growth, predation, mortality, reproduction, movement, fishing
  schema/        # Parameter definitions + registry (223 params)
  config/        # Config reader/writer (OSMOSE .csv/.properties format)
  calibration/   # pymoo NSGA-II, GP surrogate, SALib sensitivity
  forcing/       # Pure CMEMS->OSMOSE forcing conversion (grid-general, LTL + physics)
  runner.py      # Async Java subprocess manager
  results.py     # CSV/NetCDF output reader (xarray)
  scenarios.py   # Save/load/compare/fork (JSON)
ui/              # Shiny UI (page_fillable + navset_pill_list sidebar)
  pages/         # One module per tab (*_ui() + *_server())
  components/    # Reusable widgets (param_form, etc.)
  charts.py      # Custom "osmose" Plotly template (ocean palette)
  styles.py      # Centralized style constants
  theme.py       # shinyswatch superhero theme
mcp_servers/     # MCP servers (Copernicus CMEMS, ICES) — env-based credentials via .env
www/
  osmose.css     # Custom CSS overlay (Nautical Observatory theme)
```

## Code Conventions
- Python 3.12+, type hints on public APIs
- Ruff for linting/formatting, line length 100
- Tests in `tests/`, run with pytest, use `.venv/bin/python`
- OSMOSE config keys are lowercase dot-separated (e.g., `species.linf.sp0`)
- Species-indexed params use `sp{idx}` placeholder in `key_pattern`, resolved via `field.resolve_key(idx)`
- Input IDs in Shiny are generated by replacing dots with underscores in key patterns

# Shell Command Rules

When writing bash commands, strictly follow these rules to avoid triggering security permission prompts:

## No backslash-escaped whitespace
- Never escape spaces with backslashes (e.g. My\ File.txt)
- Always use double quotes around paths containing spaces: "My File.txt"
- Quote all variable expansions and file paths as a default habit
- This avoids the "Contains backslash-escaped whitespace" security block

## No $() command substitution
- Never use $() or backtick substitution in inline bash commands
- Instead, run the inner command first as a separate bash call, read its output, then use the literal value in the next command
- When possible, rewrite using pipes and xargs (e.g. pgrep python | xargs kill instead of kill $(pgrep python))

## No ${} parameter substitution
- Never use ${} parameter expansion in inline bash commands (e.g. ${VAR}, ${VAR:-default}, ${#VAR}, ${VAR%%pattern})
- Instead, use plain $VAR when a simple variable reference is needed
- If you need string manipulation like trimming or defaults, do it in a prior step and store the result in a variable, or write the logic to a temporary .sh script and execute that
- For complex variable operations, prefer a Python one-liner or a separate script file

## No multi-line commands with comments
- Never include # comments inside inline multi-line bash commands
- If a command requires multiple lines with comments, write it to a temporary script file in /tmp/ and execute that file instead
- Prefer collapsing short multi-line commands into a single line joined with &&

## No quoted newlines followed by # lines
- Never produce a bash command where a quoted string contains a newline followed by a line starting with #
- This pattern triggers the "quoted newline followed by a #-prefixed line" security block
- If you need multi-line strings that include comment-like lines, write them to a file first using a separate bash call, or use printf instead of echo with literal newlines
- Avoid heredocs (cat << EOF) that contain # lines inside inline bash commands; write the content to a file in a prior step instead

## No output redirection with >
- Never use > or >> to redirect output to files in inline bash commands
- Instead, use the Write/Edit file tool to create or modify files directly
- If command output needs to be saved, run the command first, read the output, then write it to a file using the file editing tool
- For cases where redirection is truly unavoidable, write the full command in a temporary .sh script and execute that

## No cd && git compound commands
- Never chain cd <path> && git <cmd>
- Use git -C <path> <cmd> instead

## General principles
- Prefer multiple simple, single-line bash calls over one complex compound command
- For anything that cannot be expressed as a clean single-line command, write a temporary .sh script and run it
- Always use double quotes around paths, variables, and arguments containing spaces or special characters

## Gotchas
- Use `.venv/bin/python`, not `python` (system python may not exist)
- `render_field()` generates Shiny input IDs from `key_pattern.replace(".", "_")` — overlapping prefix filters can cause duplicate IDs (see commit ca4a04c)
- `pyproject.toml` requires `[tool.setuptools.packages.find]` with `include = ["osmose*"]` — without it, setuptools finds `ui/` and `data/` and refuses to build
- Config reader auto-detects separator per line (`;`, `=`, `,`, `:`, tab) — don't assume a single separator
- Runner tests use `_ScriptRunner` subclass with mock Python scripts as fake JARs
- SALib uses `SALib.sample.sobol` (not deprecated `saltelli`)
- `import ui.charts` in page modules shadows `from shiny import ui` — register templates in `app.py` only
- `navset_pill_list` doesn't accept bare strings as section headers — use `ui.nav_control()` wrapper
- `EngineConfig.from_dict` validates keys against `osmose/engine/config_validation.py`'s allowlist (schema + AST walk of `config.py` + `_SUPPLEMENTARY_ALLOWLIST` for reader-injected metadata / legacy aliases). When adding a new config key the engine reads, the AST walker should capture it automatically; if it doesn't (e.g., key built from a caller-arg `key_pattern`), add to `_SUPPLEMENTARY_ALLOWLIST` rather than extending the walker. Integration test: `tests/test_engine_config_validation.py::test_from_dict_warn_mode_clean_on_example_configs[*]` must stay warning-free.
- **RNG reproducibility** is Python-side only. `simulation.rng.fixed=true` makes a single config + seed reproducible across Python-engine runs. It does NOT produce bit-equal outputs against the Java engine — NumPy uses PCG64, Java uses MT19937, the streams diverge on the first draw. Cross-engine equivalence is "within 1 OoM" per the parity tests (14/14 EEC, 8/8 BoB). For bit-exact Java parity, set `OsmoseCalibrationProblem(use_java_engine=True)`. See `osmose/engine/rng.py` module docstring.
- **Multi-value (`;`-separated) config entries** like `2.3;1.8` (per-stage arrays) cannot be edited via the auto-generated single-value forms. `render_field` (`ui/components/param_form.py`) detects `;` in the config value and renders a read-only text input labelled "multi-value — edit in Advanced". The Advanced tab is the editing surface for these. The reverse-side guard at `ui/state.py:sync_inputs` (`if ";" in old_val and ";" not in new_val: preserve`) prevents accidental flattening if a single-value input somehow tries to overwrite. H12 (2026-05-06).

- **`persists` in `scripts/baltic_stability_certify.py` measures the FINAL DECADE** minimum, not the whole run (since `556ba3d`, 2026-08-01). It previously used the whole-run minimum, which is dominated by the Baltic seeding bootstrap — so it was reporting the *initialisation transient* as a stability verdict while `in_envelope` used the final-decade mean. The two halves of each verdict described different windows. **Certification notes dated before 2026-08-01 are affected**: any row reading `persists ✗` with `in-envelope ✓` is a bootstrap artifact, not a collapse. Recurring across every prior note: cod (both stocks), sprat, flounder, perch. The current config re-certifies at **7/9**, not the previously reported 2/9, with no species collapsing at equilibrium. Audit: `docs/baltic_certification_reread_2026-08-01.md`.
  - **But an artifactual signal does not mean the decision it prompted was wrong.** `cod_east`'s M was lowered 1.2546 → 0.9 partly on the faulty flag; testing the revert showed M=0.9 is nonetheless required for the *mean* (at 1.2546 the stock sits ~5.6× below its ICES envelope). Test each such decision individually rather than unwinding on the audit alone.
  - When changing this criterion, update **both** `_species_row` (Python) and `java_table_from_series` (Java) or the two engines stop being comparable.

- **Bottom-oxygen -> benthos K coupling** (spec Phase 2a, adopted 2026-08-09) is live in the production Baltic config via `data/baltic/baltic_param-oxygen.csv` (included as `osmose.configuration.oxygen` in `baltic_all-parameters.csv`). `ltl.oxygen.benthos.enabled=true` scales the K (carrying capacity) of the resource named by `ltl.oxygen.benthos.rsc` (`"Benthos"`, matched by name not sp-index) by `f_o2_hill(o2, c50=60, n=3)` (`osmose/engine/processes/oxygen_function.py`) each step, applied in `ResourceState.update()` (`osmose/engine/resources.py`) before the depletable/reset branch. Forcing: `oxygen.filename=baltic_oxygen_bottom.nc`, var `o2b`, mmol O2 m⁻³ — loaded by `osmose.engine.simulate._load_oxygen_data`, called unconditionally (independent of the bioen gate) before `ResourceState` is constructed. **The forcing file MUST carry exactly `simulation.time.ndtperyear` frames (24 for Baltic)** — `PhysicalData.get_grid`/`get_value` index `step % <loaded array's frame count>`, not the declared `oxygen.nsteps.year` (metadata only), so a mismatched frame count would silently misalign the month-to-step mapping partway through the year; `_load_oxygen_data` raises `ValueError` on a mismatch rather than let that happen silently. Gate report: `docs/baltic_hypoxia_benthos_ab_2026-08-09.md` (GATE off/o2on both PASS; cod_east -21.4%, flounder -18.7%). Certification: `docs/baltic_hypoxia_certification_2026-08-09.md`.
  - **Java reads `oxygen.*` too, but only as bioenergetics (`f_o2`) forcing — it has no benthos-K coupling to apply it to.** So `scripts/baltic_stability_certify.py`'s `JAVA_INCOMPATIBLE_PINS` pins `ltl.oxygen.benthos.enabled` off for the `--java` cross-check arm (the `oxygen.*` forcing keys themselves are NOT pinned — Java legitimately reads those), and `osmose/runner.py:java_engine_block_reason` unconditionally blocks a direct Java run of any config with the coupling flag on. Demo variants that overlay the Baltic config (`baltic_a2`, `baltic_depensation`) deliberately do **not** include `osmose.configuration.oxygen` — stacking the coupling with depletable plankton or the depensation gate has never been A/B gated.
