The production OSMOSE web app is a **systemd service `osmose-shiny.service`** ("OSMOSE Python Shiny App (direct Uvicorn)"): `uvicorn app:app --host 127.0.0.1 --port 8838 --root-path /osmose`, run as user `shiny` from `/opt/micromamba/envs/shiny/bin/python3` (the micromamba `shiny` env, Python 3.13). osmose is NOT pip-installed in that env — it imports from the source tree (cwd on sys.path). **As of 2026-06-17 the source tree is a DEDICATED CLONE** at `/srv/shiny-server/osmose-src` (WorkingDirectory `/srv/shiny-server/osmose` → symlink → it), NOT the dev working tree anymore — see [[project-prod-clone-otel-getsourcelines]] for why (editing the dev tree under the running process crashed sessions). Externally proxied by nginx at `/osmose/`. Restart: **`sudo systemctl restart osmose-shiny.service`** (needs sudo; drops live sessions). A separate `shiny-server.service` + `shiny_aquabc.service` also exist; the telemac-viewer app (port 8765) is unrelated.

**▶▶ DURABLE GOTCHA (diagnosed 2026-06-15):** a plain `git pull` does NOT update the running app — systemd uvicorn loads modules once at startup with NO `--reload`. Worse, the engine **lazily imports** `osmose.engine.processes.mortality` *inside* `simulate.py:_mortality()` (line ~198), not at module load. So a long-running process keeps an OLD `osmose.engine.config` (imported at startup) in memory while picking up NEW `mortality.py` the first time a sim runs after the disk source changed. When the new field set diverges (e.g., `fr_shape`/`fr_halfsat` added by the functional-response feature on 2026-06-01 17:09), the new mortality reads `config.fr_shape` on an EngineConfig built by the stale `from_dict` that never set it → **`'EngineConfig' object has no attribute 'fr_shape'`** at run time, ONLY through the long-running GUI (fresh scripts / e2e in a fresh app process work fine). The real symptom was a process started 2026-06-01 11:44 (before the 17:09 fr_shape commit) still serving 2 weeks later.

**RULE: deploy with `cd /home/razinka/osmose/osmose-python && sudo bash deploy.sh`** (fetches origin/master into the prod clone, checks it out, provisions the Java JAR, and restarts). `sudo bash deploy.sh --restart` restarts only. A bare `sudo systemctl restart osmose-shiny.service` reloads in-memory code but does NOT pull new code into the clone. If a GUI-only `AttributeError`/missing-field error appears that cannot be reproduced from a fresh `.venv` script run, suspect the stale service FIRST — check `ps -o lstart= -p <pid>` against the commit that added the field. `EngineConfig.from_dict` is the ONLY constructor and sets every field unconditionally (`config.py:~1986`), so a missing-attribute error is never a from_dict bug — it's a stale in-memory module.
