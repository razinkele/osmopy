# OSMOSE 4.4.0 Jar Swap — Design

> Final step of the config-key migration to OSMOSE 4.4.0. PR1 (`001c530`, #77) shipped the core alias layer; PR2 (`dc2d701`, #78) wired the UI/writer/calibration so the internal model is fully 4.4.0 while writes reverse-map to 4.3.x for the bundled 4.3.3 jar. This swap replaces the bundled jar with 4.4.0 and flips OSMOPY to write **native** 4.4.0 configs.

## Goal

Bundle `osmose_4.4.0-jar-with-dependencies.jar`, make OSMOPY write native 4.4.0 config keys, validate (via A/B against the 4.3.3 jar) that 4.4.0 in legacy mode does not change engine results for OSMOPY's existing configs, then hard-replace the 4.3.3 jar.

## Scope boundary (explicit)

This swap makes the **Java engine** 4.4.0 and OSMOPY's writes **native 4.4.0**. It does **NOT** add support for any of 4.4.0's *new features* (stochastic maturity ogive, post-reproduction mortality, density-dependent / region-aware mortality, gradient-based movements, background-species overhaul + biomass multipliers, new egg-size bioen, simplified bioenergetics, functional bioeconomics, `simulation.fixed.seed.enabled`, `simulation.nschool.multiplier`, reworked restart). Those are deferred — each its own future spec (schema fields + Python-engine implementation).

**Engine-divergence consequence (by design, documented, not fixed here):** OSMOPY's primary engine is the pure-Python engine, which implements 4.3.x-era science and none of the 4.4.0 features.
- Configs that do **not** enable any 4.4.0 feature (every current OSMOPY config — PR2's schema only *renamed* existing keys, added no new-feature fields): Python (4.3.x) ≈ Java (4.4.0 legacy mode) → cross-engine parity holds.
- Configs that enable a 4.4.0-only feature: only the Java engine honors it; the Python engine cannot → divergence by design. The UI exposes no 4.4.0-only feature today, so there is no immediate divergence; this is recorded as a known limitation.

## Background facts (verified)

- The 4.4.0 fat-jar is a downloadable GitHub release asset: `osmose_4.4.0-jar-with-dependencies.jar`, repo `github.com/osmose-model/osmose`, release **v4.4.0** (2026-05-21). Bundled jar is git-tracked in `osmose-java/` (24 MB).
- All 4.4.0 new capabilities are **opt-in** (config-flag gated, e.g. `species.maturity.mode`, `species.bioenergetics.model`, `simulation.fixed.seed.enabled`). A config that does not set them runs in legacy mode.
- `ui/pages/run.py` auto-discovers the jar by globbing `osmose-java/*.jar` → two jars present is ambiguous. The cutover removes the 4.3.3 jar so exactly one remains.
- Java parity tests are `@pytest.mark.java`, **skipped in CI** (`_java_available = shutil.which("java") and JAR_PATH.exists()`, `tests/test_engine_java_comparison.py:44`). The swap therefore does **not** turn CI red; parity is validated **locally**.
- The Python-engine parity baselines (`tests/baselines/*.npz`, via `scripts/save_parity_baseline.py`) are Python-only and **unaffected** by a jar swap — do NOT regenerate them.
- The 4.4.0 `-update` config-migration crashes on OSMOPY configs (IndexOutOfBoundsException, found during PR1) — irrelevant here because OSMOPY writes native 4.4.0 keys, so no `-update` is invoked.
- Hardcoded `4.3.3` references to update: `ui/state.py:42` (default `jar_path`), `tests/test_state.py:79` (asserts it), `tests/test_engine_java_comparison.py:39` (`JAR_PATH`), `scripts/validate_engines.py:23` (`JAR_PATH`), `osmose/demo.py:228` (`migrate_config` default `target_version` — verify), and docstrings `osmose/engine/timeseries.py:4` ("Matches Java OSMOSE 4.3.3") + `osmose/engine/processes/foraging_mortality.py:11` (stale bioen ingestion key).
- The PR2 writer/`write_temp_config`/calibration reverse-map default is currently `target_version="4.3.3"`. `to_target_keys(cfg, "4.4.0")` is identity + an `osmose.version=4.4.0` stamp (no key changes). Flipping the default to `"4.4.0"` therefore makes writes emit native 4.4.0 keys with no other behavior change in the writer itself.

## Architecture — three phases

The work is strictly ordered: Phase A is a gate; Phases B and C run only if A passes.

### Phase A — Obtain the jar + A/B validation (GATE)

1. **Obtain the jar.** Fetch `osmose_4.4.0-jar-with-dependencies.jar` into `osmose-java/` via `gh release download v4.4.0 -R osmose-model/osmose -p '*jar-with-dependencies*'` (or curl the asset URL). If the environment has no network access to the asset, fall back to the user placing the file. Sanity-check: file size ≈ 24 MB and `java -jar osmose-java/osmose_4.4.0-jar-with-dependencies.jar` prints usage/version without error.

2. **A/B engine comparison.** With BOTH jars present temporarily, run the `eec_full` example two ways, invoking each jar by **explicit path** (NOT via the `run.py` `*.jar` glob, which is ambiguous with two jars):
   - 4.3.3-Java: config written with `target_version="4.3.3"` (old keys).
   - 4.4.0-Java: config written with `target_version="4.4.0"` (native new keys).
   Compare the headline outputs (biomass, abundance, yield time series per species). Because the new features are opt-in and `eec_full` enables none, the two runs are expected to be **near-identical** (allowing only RNG-stream differences if seeds/streams differ — prefer a fixed seed and compare within a tight relative tolerance; fall back to the established "within 1 order of magnitude" cross-engine bar if RNG differences dominate).
   - Also re-run the existing **Python-vs-4.4.0-Java** cross-engine check (`scripts/validate_engines.py` pointed at the 4.4.0 jar) and confirm it still passes the within-1-OoM bar.

3. **Decision gate.** If both comparisons pass tolerance → proceed to Phase B. If a comparison diverges, investigate which 4.4.0 default changed (a non-opt-in behavior change), document it in the spec/changelog, and decide whether to (a) pin the legacy behavior via a config flag, or (b) accept + document the change — before cutting over. Do not flip the write-default until this gate is green.

### Phase B — Cutover (only after Phase A passes)

4. **Remove the 4.3.3 jar.** `git rm osmose-java/osmose_4.3.3-jar-with-dependencies.jar`. Only the 4.4.0 jar remains → the `run.py` glob is unambiguous.

5. **Flip the write-default to 4.4.0.** Change `target_version="4.3.3"` → `"4.4.0"` in:
   - `osmose/config/writer.py::OsmoseConfigWriter.write`
   - `ui/pages/run.py::write_temp_config`
   - `osmose/calibration/problem.py::_run_java_subprocess` (the `-P` override reverse-map call)
   With target 4.4.0, `to_target_keys` is identity + version stamp, so OSMOPY writes native 4.4.0 keys and the jar reads them directly.

6. **Extend the writer ROUTING table.** `OsmoseConfigWriter.ROUTING`/`MASTER_PREFIXES` currently route by OLD prefixes. Now that the multi-file writer emits NEW keys (no reverse-map), add routes for the NEW prefixes so **Export config** (and any multi-file write) buckets them correctly: `module.*` (global toggles → master/module file), `output.fisheries.*` (→ output file), `simulation.restart.*` (→ restart/simulation file), bioen `species.maturity.{eta,r,m0,m1}.*` (→ bioenergetics file). Route to the destination the 4.4.0 sub-file convention expects; when unsure, route to master (4.4.0 reads a flat all-parameters file fine). NOTE: the Java **run** path uses the flat `write_temp_config`, so ROUTING does not affect runs — only Export/multi-file output.

7. **Update hardcoded `4.3.3` references** to `4.4.0`:
   - `ui/state.py:42` (default `jar_path`), `tests/test_state.py:79` (assertion), `tests/test_engine_java_comparison.py:39` (`JAR_PATH`), `scripts/validate_engines.py:23` (`JAR_PATH`).
   - `osmose/demo.py:228` `migrate_config` default `target_version` — verify what it controls; if it sets the canonical internal target, it should already be (or become) `4.4.0`.
   - Docstrings: `osmose/engine/timeseries.py:4` (reword — the Python engine implements 4.3.x-era behavior, so state that accurately rather than claiming it "matches 4.4.0"); `osmose/engine/processes/foraging_mortality.py:11` (update the stale bioen ingestion key to the unified `predation.ingestion.rate.max.sp{i}`).

### Phase C — Tests + docs

8. **Tests.**
   - New unit test: with no explicit `target_version`, the writer/`write_temp_config` now emit NATIVE 4.4.0 keys (e.g. `module.bioenergetics.enabled` present, `simulation.bioen.enabled` absent on disk); and `to_target_keys(cfg, "4.4.0")` returns identity + the version stamp.
   - Update the jar-ref assertion in `tests/test_state.py:79` to the 4.4.0 path (this test skips in CI without the jar but must pass locally / wherever the jar is present).
   - Full suite green; CI unaffected (Java-marked tests still skip without a jar).

9. **Docs.**
   - Update the cross-engine parity note (CLAUDE.md RNG/parity section and/or `docs/parity-roadmap.md`): cross-engine equivalence is now 4.4.0-Java (legacy mode) vs the Python engine, within 1 OoM; record the by-design divergence-on-new-features limitation.
   - CHANGELOG entry: bundled engine upgraded to OSMOSE 4.4.0; OSMOPY now writes native 4.4.0 configs; note the deferred new-feature support.

## Error handling / risks

- **Network fetch fails (Phase A.1):** fall back to the user placing the jar at the expected path; the rest of the plan proceeds once the binary is present.
- **A/B divergence (Phase A.2):** the gate catches a non-opt-in 4.4.0 behavior change; investigate + document/decide before cutover (do not silently re-baseline).
- **Stale 4.3.3 jar in a deployed clone:** the `run.py` glob would see two jars. The deploy step (`deploy.sh` / prod clone) must ensure the old jar is removed on pull; note this for the prod redeploy.
- **`to_target_keys("4.4.0")` version stamp:** writes `osmose.version=4.4.0` to disk — correct for the 4.4.0 jar (consistent with PR2 behavior, which stamped the target version).

## Testing strategy

- **Local A/B + cross-engine validation (Phase A gate):** `eec_full` on 4.3.3-Java vs 4.4.0-Java within tolerance; Python vs 4.4.0-Java within 1 OoM. Requires Java + both jars; manual/local, not CI.
- **Unit (CI):** write-default-4.4.0 test; updated `test_state.py` jar assertion; full suite green. Java-marked tests skip in CI as before.
- **Python-engine `.npz` baselines:** unchanged, not regenerated.

## Out of scope (future work, each its own spec)

- Schema fields + Python-engine implementation for any 4.4.0 new feature (stochastic maturity, post-repro mortality, gradient movements, simplified bioen, biomass multipliers, functional bioeconomics, etc.).
- A runtime engine-version selector / dual-jar support.
- Prod redeploy (`sudo bash deploy.sh`) — operational step requiring user sudo; the prod clone must drop the old jar on pull.
