# OSMOSE 4.4.0 Jar Swap + Value Migration — Design

> Final step of the config-key migration to OSMOSE 4.4.0. PR1 (`001c530`, #77) shipped the alias core; PR2 (`dc2d701`, #78) wired the UI/writer/calibration so the internal model is 4.4.0 with writes reverse-mapped to 4.3.x for the bundled 4.3.3 jar. This step bundles the 4.4.0 jar, makes OSMOPY write **native** 4.4.0 configs, and adds a **value-migration layer** for the non-opt-in unit/semantic changes 4.4.0 introduced — then validates and hard-replaces the jar.
>
> An in-loop spec review (4 angles, source-verified against the OSMOSE engine at tags `4.3.3`/`v4.4.0`) corrected the original "simple jar swap" framing: 4.4.0 silently reinterprets larval-mortality units, the jar is git-ignored (not tracked), the run.py glob deterministically picks the OLD jar, and the Python engine is already partly-4.4.0. This revision incorporates all of that.

## Goal

Bundle `osmose_4.4.0-jar-with-dependencies.jar`; make OSMOPY write native 4.4.0 configs with value migrations that preserve engine behavior; validate via A/B (4.3.3-Java vs 4.4.0-Java, after rescale) + the existing Python-vs-Java check; then remove the 4.3.3 jar and flip the write-default to 4.4.0.

## Scope boundary (explicit)

In scope: bundle the 4.4.0 jar; native-4.4.0 write path; a value-migration layer for the **non-opt-in** 4.4.0 changes that affect OSMOPY's configs (enumerated below from a source-verified audit); validation; cutover.

Out of scope (each its own future spec): support for 4.4.0 *opt-in* new features (stochastic maturity ogive, post-repro mortality, density-dependent/region-aware mortality, gradient movements, background-species overhaul + biomass multipliers, egg-size bioen, simplified bioenergetics, functional bioeconomics, `simulation.fixed.seed.enabled`, `simulation.nschool.multiplier`); a runtime dual-jar selector; restart-file support (OSMOPY uses no restart in any run path — confirmed).

## Engine-divergence framing (corrected)

OSMOPY's primary engine is the pure-Python engine. After PR1 it already **reads 4.4.0 key names** (`osmose/engine/config.py`: `module.bioenergetics.enabled` :1865, `module.multispecies.fisheries.enabled` :1532, `module.genetics.enabled` :1922, `species.maturity.{eta,r,m0,m1}` :1881-84) and has **already adopted one 4.4.0 semantic** — the unified `predation.ingestion.rate.max.sp{i}` (:606) driving both predation and the energy budget. So the accurate statement is: *the Python engine implements 4.3.x-era science EXCEPT the bioen ingestion-unification (already 4.4.0), and consumes 4.4.0 key names.* Do NOT re-assert "pure 4.3.x" (e.g. in the `timeseries.py` docstring).

Consequence: for bioen/Ev-OSMOSE configs, cross-engine parity is **currently mismatched** (Python unified vs the bundled 4.3.3 jar's split keys); the 4.4.0 jar **aligns** it. The swap closes a gap rather than opening one. For non-bioen configs that enable no opt-in feature (eec_full, every current OSMOPY config), Python ≈ Java(4.4.0 legacy) once the value migrations below are applied. A config that enables a 4.4.0-only opt-in feature would diverge by design (the Python engine can't honor it) — but the UI exposes none today, so there is no immediate divergence.

## Audit — non-opt-in 4.4.0 changes (source-verified at tag v4.4.0)

This drives the value-migration layer. Citations are engine files at `github.com/osmose-model/osmose`. eec_full checked locally (`data/eec_full/`: `ndtPerYear=24`, bioen OFF, fishing ON, LTL resource, maps movement).

**Value migrations (apply when writing native 4.4.0; reverse when reading a native-4.4.0 config):**

1. **Larval additional mortality units changed (per-step → per-year). AFFECTS eec_full.** `AnnualLarvaMortality.init()` v4.4.0 multiplies the base rate by `... / nStepYear`; 4.3.3 did not. So `mortality.additional.larva.rate.spX` is now rate/year. Migration: ×`simulation.time.ndtperyear` on write to 4.4.0 (÷ndt on read from a native-4.4.0 config). eec_full sets this key for all 14 species → affected.
2. **Per-timestep larval file variant `ByDtLarvaMortality` units changed (CONDITIONAL — eec_full not affected).** v4.4.0 `init()` does `mortRate[t] /= nStepYear`. So a `mortality.additional.larva.rate.byDt.file.spX` time series is now per-year. Migration: ×ndt on write to 4.4.0, only when that key family is present. (The new optional density term defaults inert.)

**"Don't-emit / drop" guards (preserve legacy behavior on 4.4.0 write):**

3. **Never emit `simulation.resources.computePercent.legacy=false`.** Default is `true` = the legacy linear LTL formula (byte-identical to 4.3.3). OSMOPY's schema does not define this key, so the guard is "ensure it is never written"; emitting `false` would switch to the new log relationship and change LTL/resource predation.
4. **Never emit `species.beta.spX` for a non-bioen species.** In 4.4.0 `species.beta` feeds the predation allometric exponent (`PredationMortality` `pow(weight·1e6, betaBioen)`); default 1 collapses to the legacy `instantaneousBiomass` form. In 4.3.3 it was read only under bioen. Guard: when bioenergetics is OFF, do not write `species.beta.spX` to a 4.4.0 config.
5. **Drop the removed `species.lmax.spX` growth cap on 4.4.0 write + document.** 4.4.0 removed the lmax growth cap (commented out in `VonBertalanffyGrowth`). A config relying on lmax to bound growth would grow unbounded on 4.4.0; there is no clean migration. Drop the key on 4.4.0 write (verify the jar tolerates/ignores it if not dropped) and document the lost-cap limitation. eec_full sets no `species.lmax`.

**Confirmed UNCHANGED for legacy configs (no migration):** adult additional mortality (`mortality.additional.rate` ÷ndt in both versions), starvation (`predation.efficiency.critical` read in both, ÷ndt in both), growth defaults (length-based, predation-success on — legacy preserved), reproduction (default oviparity numerically equivalent), fishing yield (4.4.0 tracks numbers internally; biomass via unchanged `abd2biom` → identical yields), and the bioen max-ingestion key (the PR1 rename; per-year ÷ndt in both — no extra migration).

**Output/cosmetic only (no migration, but may shift reported series slightly):** `SimulationStep` reordering (movement before `indicators.initStep`), NetCDF chunking default → "standard", region dimension added to mortality output arrays, `lastYear`/`lastAge` now inclusive.

## Value-migration layer — design

**Units convention:** the internal canonical config stores **4.3.x / per-timestep** larval-rate semantics (the Python engine consumes them that way; every OSMOPY example config is authored that way). Transforms are applied only at the I/O boundary, parameterized by `simulation.time.ndtperyear` read from the same config.

- **Write to 4.4.0** — `to_target_keys(cfg, "4.4.0")`: after the (identity) key step, multiply each present larval-rate key (items 1, 2) by `ndtperyear`; apply guards 3–5 (ensure `computePercent.legacy=false` absent; drop non-bioen `species.beta.spX`; drop `species.lmax.spX`).
- **Write to 4.3.3** — `to_target_keys(cfg, "4.3.3")`: larval rate already per-timestep internally → no value change (only the existing key reverse-map).
- **Read** — `canonicalize_config(cfg)`: if the source declares `osmose.version >= 4.4.0`, divide the larval-rate keys by `ndtperyear` (a native-4.4.0 config stores per-year) to reach the internal per-timestep value; for a 4.3.x source, no value change. Round-trip-safe: read-4.4.0 (÷ndt) → write-4.4.0 (×ndt) is identity; read-4.3.x (no-op) → write-4.4.0 (×ndt) → the 4.4.0 jar's internal ÷ndt → original per-timestep value.

**Where:** extend `osmose/config/aliases.py`. Add a `VALUE_MIGRATIONS_440` description (the larval keys + their transform) and a helper applied inside `to_target_keys` and `canonicalize_config`, after the key-rename step. Guard: if `simulation.time.ndtperyear` is absent, skip the value transform and emit a warning (do not silently corrupt). The transforms must be exact-inverse (a unit test asserts `read(write(x)) == x` for a config carrying larval keys).

**Version-match hardening:** `to_target_keys`'s `target_version == "4.4.0"` branch is an exact string match; a `"4.4.0-SNAPSHOT"`/whitespace value would fall through to the reverse branch and corrupt a native config. Add an assertion/normalization so only an exact recognized version selects identity+value-migration.

## Architecture — phases (Phase B gates the cutover)

### Phase A — Value-migration layer (CI-testable, jar-independent)
1. Implement `VALUE_MIGRATIONS_440` + the larval ×ndt / ÷ndt transforms and guards 3–5 in `osmose/config/aliases.py`, wired into `to_target_keys` and `canonicalize_config`.
2. Unit tests (CI): larval round-trip exact-inverse; `to_target_keys(cfg,"4.4.0")` multiplies the larval key by ndt and leaves a 4.3.3 write unchanged; guards drop `species.beta`(non-bioen)/`species.lmax` and never emit `computePercent.legacy=false`; ndt-absent path warns + skips; version exact-match hardening.

### Phase B — Obtain jar + A/B validation (GATE; requires Java, local-only)
3. **Obtain the jar.** `gh release download v4.4.0 -R osmose-model/osmose -p '*jar-with-dependencies*'` (or curl the asset) into `osmose-java/`. Fallback: user places it. The jar is **git-ignored** (`.gitignore:61` `osmose-java/*.jar`) — it lives in the working tree only, never committed. Sanity: ≈24 MB; `java -jar <jar>` prints usage.
4. **A/B engine comparison** (both jars temporarily present; invoke each by EXPLICIT path, not the run.py glob). Run `eec_full` on:
   - 4.3.3-Java fed a `target_version="4.3.3"` config (old keys, raw larval value).
   - 4.4.0-Java fed a `target_version="4.4.0"` config (native keys, larval value ×ndt per Phase A).
   With the value migration applied, the two should agree. Compare per-species **biomass, abundance, yield, AND size-structure / mean-TL** (the headline-only gate is too narrow; the SimulationStep reorder can shift series slightly). Tolerance: ensemble/structural — same-seed bit-equality is NOT achievable (`simulation.fixed.seed.enabled` defaults false → nondeterministic seeding; RNG draw-order changed), so use the established **within-1-order-of-magnitude per-species** bar (the one `scripts/validate_engines.py` already uses), or N-replicate ensemble means with overlapping CIs.
   - Also re-run **Python-vs-4.4.0-Java** (`scripts/validate_engines.py` pointed at the 4.4.0 jar) within 1 OoM.
   - Add a **second config shape to the A/B set** (a fishing-enabled, non-background config beyond eec_full) so the `output.fisheries.*`/`module.multispecies.fisheries.enabled` path is exercised. Bioen configs (baltic_ev) are Java-blocked (`nbackground>0`, Python-engine-only) and cannot be A/B'd on Java — the compensating control is the existing Python-side bioen parity test (PR1/PR2), which already covers the ingestion-unification.
5. **Decision gate.** Pass → Phase C. Diverge → identify the offending 4.4.0 default (the audit missed something), extend the value-migration layer or document/accept, before cutover.

### Phase C — Cutover (only after Phase B passes)
6. **Remove the 4.3.3 jar:** plain `rm osmose-java/osmose_4.3.3-jar-with-dependencies.jar` (NOT `git rm` — it is untracked). Nothing to commit for the binaries.
7. **Make jar selection version-aware (code guard, not a deploy note):** in `ui/pages/run.py` (the `sorted(JAR_DIR.glob("*.jar"))[0]` at ~:562, which lexically picks 4.3.3 over 4.4.0), select the **highest-version** jar (e.g. `sorted(..., reverse=True)[0]` or a version-key sort) so a lingering 4.3.3 jar is harmless. Update the hardcoded default in `ui/state.py:42` to the 4.4.0 path.
8. **Flip the write-default to 4.4.0:** `target_version="4.3.3"`→`"4.4.0"` in `osmose/config/writer.py::write` (:63, + docstring :77-80), `ui/pages/run.py::write_temp_config` (:136), and the **literal** `to_target_keys(dict(overrides), target_version="4.3.3")` at `osmose/calibration/problem.py:458` (+ its comment :455). Keep `osmose/config/aliases.py:93`'s generic library default at `"4.3.3"` (callers pass the target explicitly).
9. **Extend `OsmoseConfigWriter.ROUTING`** for native-4.4.0 multi-file Export (run path uses the flat `write_temp_config`, so this is Export-only): route `module.*` (currently falls through to master — fine, confirm), and re-home `species.maturity.{eta,r,m0,m1}.*` (currently matched by the `species.` route → species file; 4.4.0 bioen maturity belongs with bioenergetics) and `output.fisheries.*` / `simulation.restart.*` (verify their current sub-file vs the 4.4.0 convention). When unsure, master is safe (4.4.0 reads a flat file). This is the most deferrable piece if Export-to-sub-files is not a validated requirement.
10. **Update remaining version refs:** `tests/test_state.py:79` (jar assertion → 4.4.0), `tests/test_engine_java_comparison.py:39` (`JAR_PATH`), `scripts/validate_engines.py:23` (`JAR_PATH`); `osmose/demo.py` `migrate_config` default `target_version` (:232) — decide + flip to `4.4.0` (the canonical internal target post-cutover) and fix its **stale docstring** (:239-240 says the chain stops at 4.3.0, but `_MIGRATION_CHAIN` now has `("4.4.0", RENAMES_440)`); docstrings `osmose/engine/timeseries.py:4` (reword accurately per the framing section) and `osmose/engine/processes/foraging_mortality.py:11` (stale bioen ingestion key); user-facing `README.md:14` & `:59` (4.3.3 → 4.4.0) and `ui/components/help_modal.py:309` (stale "since 4.3.3" note — optional).

### Phase D — Deploy + docs
11. **Deploy guard:** `deploy.sh:137-142` copies `osmose-java/*.jar` by glob but `cp -f` does NOT delete a pre-existing old jar in the prod clone, and the build context must contain the (git-ignored) jar. Add an explicit `rm` of the old jar in BOTH the dev `SOURCE_DIR` and the prod clone to the deploy step. The `Dockerfile:32` `COPY osmose-java* osmose-java/` glob auto-adapts but needs the jar present in the build context (it is git-ignored). The version-aware glob (step 7) is the durable safeguard.
12. **Docs:** update the cross-engine parity note (CLAUDE.md / `docs/parity-roadmap.md`) — 4.4.0-Java legacy-mode vs Python within 1 OoM, with the corrected divergence framing + the value migrations recorded; CHANGELOG entry (engine → 4.4.0; native-4.4.0 writes with larval-units value migration; deferred new-feature support).

## Error handling / risks

- **Network fetch fails (B.3):** user places the jar; rest proceeds.
- **A/B divergence after rescale (B.5):** the gate catches an audit miss; extend the value layer or document before cutover — do not silently re-baseline.
- **ndt absent for a config with larval keys:** value transform skipped + warning (don't corrupt); document.
- **Stale 4.3.3 jar in a clone:** the version-aware glob (step 7) makes it harmless; deploy also `rm`s it (step 11).
- **`-update` crash:** not a run-path risk — `runner.py` only passes `-update` via the dead/test-only `migrate()` (`runner.py:245`); normal runs never invoke it. The real invariant is "every Java-bound write is native-4.4.0," so the 4.4.0 jar's load-time auto-migration is a no-op (`osmose.version=4.4.0` ≥ jar version → up-to-date). The A/B's 4.3.3-keys arm must run on the **4.3.3** jar (feeding old keys to the 4.4.0 jar would trip its crashing load-migration).
- **No Git LFS, no packaging change:** jar is git-ignored and not package-data (no `MANIFEST.in`; `pyproject` packages only `osmose*`) — confirmed, no edits needed there.

## Testing strategy

- **CI (jar-independent):** the Phase A value-migration unit tests; a durable tripwire asserting the post-cutover write-default is native-4.4.0 and `to_target_keys(cfg,"4.4.0")` applies identity-keys + larval ×ndt; `EngineConfig.from_dict` still reads the unified ingestion value. Java-marked tests (`@java_required` skipif, `tests/test_engine_java_comparison.py:44-45` — note: a skipif, not a registered marker) skip in CI as before. Full suite green.
- **Local (Phase B gate, needs Java + both jars):** eec_full 4.3.3-Java vs 4.4.0-Java (post-rescale) + a second fishing config, within 1 OoM / ensemble; Python-vs-4.4.0-Java within 1 OoM.
- **Python `.npz` baselines:** unchanged, not regenerated (Python-only, jar-independent).

## Out of scope (future, each its own spec)

4.4.0 opt-in new features (schema + Python-engine impl); dual-jar runtime selector; restart-file support; the `species.lmax` growth-cap behavior (removed upstream — no clean migration, documented as a limitation).
