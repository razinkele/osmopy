# Adapt Baltic background species to OSMOSE 4.4.x keys — design

> Status: design (awaiting review) · 2026-06-29
> Make the Baltic example **load + complete a run on the Java OSMOSE 4.4.1 jar** by extending the
> 4.4.x config migration to emit the background-species keys that 4.4.x's `BackgroundSpecies.init()`
> requires for Baltic's GreySeal/Cormorant top predators. Write-path / migration only — **no
> Python-engine or dynamics change**, and the default write-target stays 4.3.3 (this is additive).
> Sub-project **A** of the larger "standardise Python setup to 4.4.x" effort (sub-project C, deferred —
> see §7).

## 1. Problem

EEC-full already runs on the 4.4.1 jar (validated). Baltic does not: staged at `target_version="4.4.1"`,
the 4.4.1 jar bumps the version + emits the LTL resource-forcing keys, but crashes at config init:
```
osmose[severe] Could not find parameter species.multiplier.sp14
java.lang.NullPointerException ... at fr.ird.osmose.background.BackgroundSpecies.<init>(BackgroundSpecies.java:240)
```
4.4.x represents background species as **size/age-class structured** and reads (per the jar's
`BackgroundSpecies.class`): `species.multiplier.spN` (or `species.multiplier.log.spN`),
`species.biomass.spN`/`species.biomass.nsteps.year.spN`, `species.nclass.spN`, `species.age.spN`,
`species.length.spN`, `species.trophic.level.spN`, `species.size.proportion.spN` (must sum to 1.0),
`species.length2weight.{condition.factor,allometric.power}.spN`, `species.beta.spN`.

**Good news (verified):** Baltic's `baltic_param-background.csv` *already carries most of this* for sp14
(GreySeal) and sp15 (Cormorant) — `nclass=2`, per-class `age`/`length`/`trophic.level`/`size.proportion`,
length-weight, and the predation ratios. So this is **not** a synthesis-from-scratch; it's emitting the
few genuinely-missing keys + fixing one format inconsistency.

## 2. What's missing / wrong (per the existing background config)

1. **`species.multiplier.spN`** — absent (the crash). 4.4.x scales background biomass by this.
2. **`species.beta.spN`** — absent (4.4.x predation allometric exponent; legacy default = 1).
3. **Biomass-forcing keys** — the config has `species.file.spN = baltic_predator_biomass.nc` but not the
   `species.biomass.{mode,file,varname,nsteps.year}.spN` keys 4.4.x's NETCDF_BIOMASS forcing wants
   (same gap the resource migration fills for `type=resource`).
4. **Separator inconsistency** — `species.trophic.level.sp14 ; 4.5, 4.8` uses **commas** while
   `species.length.sp14 ; 110;170` and `species.size.proportion`/`species.age` use **semicolons**. With
   `nclass=2`, 4.4.x's consistency check ("Length of species.trophic.level.spN is not consistent with
   species.nclass") can fail if TL parses as 1 value. Normalize the per-class arrays to `;`-separated.

## 3. Approach (`osmose/config/aliases.py`)

Add `_emit_background_species_keys(cfg)`, called from the `>=4.4.0` branch of `to_target_keys`
(alongside `_emit_resource_biomass_forcing`; additive, inert on the 4.3.3 path). For each
`species.type.spN == "background"`:

- **Emit `species.multiplier.spN`** if absent → `"1"` (a single scalar; no biomass scaling). If the jar
  later demands a per-class form, emit `"1;1"` (matching `nclass`) — resolved iteratively (§4).
- **Emit `species.beta.spN`** if absent → `"1"` (legacy allometric default).
- **Emit the biomass-forcing keys** (`species.biomass.mode/file/varname/nsteps.year.spN`) from
  `species.file.spN` — generalize the existing `_emit_resource_biomass_forcing` to also cover
  `type=background`, or call a shared helper, so resource + background share one code path.
- **Normalize per-class array separators**: rewrite `species.trophic.level.spN` (and any other per-class
  array using commas) to `;`-separated, so all of `age`/`length`/`trophic.level`/`size.proportion` use
  the same delimiter and match `nclass`.
- **Preserve** the existing `nclass`/`age`/`length`/`size.proportion`/`length2weight`/predation keys
  verbatim (do not regenerate — the config's values are intentional).

Defensive: only emit a key when absent (`setdefault`), never overwrite an author-provided value.

## 4. Iterative jar-as-oracle resolution

The exact full set 4.4.x demands is confirmed empirically, not guessed. Loop: stage Baltic at 4.4.1 →
run the 4.4.1 jar → read the next `severe`/`NullPointerException`/"not consistent" error → add the
corresponding emit/normalization to `_emit_background_species_keys` → repeat until a clean run. The run
proceeds past config init into the **predation/fishery stage**, which may surface the background species
in the catchability/discards/predation-accessibility matrices (the original 4.3.3 blocker — Baltic stores
comma-separated fishery matrices and may omit the background columns). Resolving those (matrix
normalization / background-column emission) is **in scope** ("runs cleanly"). Each requirement becomes an
explicit, commented emit — no silent guesses.

## 5. Validation

- **Unit (`tests/test_config_aliases.py` or similar):** `to_target_keys(baltic_cfg, "4.4.1")` for a
  `type=background` species emits `species.multiplier.spN`, `species.beta.spN`, and the
  `species.biomass.*.spN` keys; the TL array becomes `;`-separated; the existing `nclass`/`age`/`length`
  values are unchanged; nothing emitted on the 4.3.3 path.
- **End-to-end harness `scripts/baltic_440_smoke.py`** (mirrors `cross_engine_parity_440.py`'s staging):
  stage Baltic at 4.4.1 → run the 4.4.1 jar for N years → assert **exit 0**, output CSVs produced, and
  **no focal species collapsed to zero biomass** (sanity that the background predators didn't break the
  food web). This is the acceptance gate for "loads + runs cleanly."
- **No parity claim** — the single-/two-class background representation is a *loadability* faithful port,
  not a calibrated Java≈Python match (Baltic is Python-calibrated + Python-only by design).
- **No Python-engine change** — `_emit_background_species_keys` only fires on the 4.4.x *write* path; the
  Python engine + the 4.3.3 default are untouched. Existing alias/migration tests stay green.

## 6. Edge cases

- A `type=background` species that already has `species.multiplier`/`beta` (author-provided) → left as-is
  (`setdefault`).
- A background species without a forcing file (`species.file.spN` absent) → skip the biomass-forcing
  emit (no NetCDF); the jar may then require a constant-biomass key — resolved iteratively if it arises.
- `nclass` vs array-length mismatch in the source config (author error) → surfaced by the jar's
  consistency check; the migration normalizes separators but does not fabricate/trim values.

## 7. Future work — sub-project C (deferred, separate cycle)

"Standardise the Python setup to OSMOSE 4.4.x" — a distinct, larger cutover to brainstorm separately, with
the user-confirmed scope: (a) flip the default write-target 4.3.3 → 4.4.x; (b) migrate bundled config
masters to native 4.4.x; (c) make the Python engine read 4.4.x semantics natively (not only on write);
(d) UI 4.4.1 engine + version-aware `java_engine_block_reason` + full cross-engine re-validation. C
depends on this sub-project A (and the BoB 365-step-forcing fix) so every config loads on 4.4.x first.

## 8. Out of scope (this spec)

- Sub-project C above (the cutover) and the BoB 365-step blocker.
- Java≈Python parity validation for Baltic (loadability + non-collapse only).
- Any change to the Python engine, the bundled config sources, or the 4.3.3 default path.
