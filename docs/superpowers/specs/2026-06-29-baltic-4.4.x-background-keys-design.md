# Adapt Baltic background species to OSMOSE 4.4.x keys — design

> Status: design (awaiting review) · 2026-06-29
> Make the Baltic example **load + run (with functioning background predators) on the Java OSMOSE 4.4.1
> jar**. Two parts: (1) a 4.4.x write-path migration emitting the background-species init keys
> `BackgroundSpecies.<init>` needs — `species.multiplier` (scalar) + `species.biomass` as an **inline
> numeric array** (not the resource NetCDF keys) + optional `beta`/`nsteps.year`; (2) **authoring the
> GreySeal/Cormorant accessibility values into the STAGED 4.4.x predation matrix** (the jar iterates them
> as predators and crashes otherwise — the 4.3.3 blocker, unchanged in 4.4.1). The canonical `data/baltic`
> source the Python engine reads stays **untouched** (staged-copy only), and the 4.3.3 default is
> unchanged — so **no Python-engine/dynamics change**. Sub-project **A** of the larger "standardise Python
> setup to 4.4.x" effort (sub-project C, deferred — see §7).

## 1. Problem

EEC-full already runs on the 4.4.1 jar (validated). Baltic does not: staged at `target_version="4.4.1"`,
the 4.4.1 jar bumps the version + emits the LTL resource-forcing keys, but crashes at config init:
```
osmose[severe] Could not find parameter species.multiplier.sp14
java.lang.NullPointerException ... at fr.ird.osmose.background.BackgroundSpecies.<init>(BackgroundSpecies.java:240)
```
4.4.x represents background species as **size/age-class structured** and reads (per the jar's
`BackgroundSpecies.class`): `species.multiplier.spN` (or `species.multiplier.log.spN`),
`species.biomass.spN`/`species.biomass.nsteps.year.spN`, `species.nclass.spN`, `species.age.spN`,
`species.length.spN`, `species.trophic.level.spN`, `species.size.proportion.spN` (must sum to 1.0),
`species.length2weight.{condition.factor,allometric.power}.spN`, `species.beta.spN`.

**Good news (verified):** Baltic's `baltic_param-background.csv` *already carries most of this* for sp14
(GreySeal) and sp15 (Cormorant) — `nclass=2`, per-class `age`/`length`/`trophic.level`/`size.proportion`,
length-weight, and the predation ratios. So this is **not** a synthesis-from-scratch; it's emitting the
few genuinely-missing keys + fixing one format inconsistency.

## 2. What's missing / wrong — TWO layers (verified against the 4.4.1 jar bytecode)

**Layer 1 — background-species init keys** (`BackgroundSpecies.<init>`):
1. **`species.multiplier.spN`** — absent (the first crash). Read as a **scalar** (`getFloat`); the jar
   does `biomass × multiplier`, so `1` = use the biomass as-is. (No per-class form — `getFloat("1;1")`
   would throw.)
2. **`species.biomass.spN`** — absent, and this is the key correction: 4.4.x reads background biomass as
   an **INLINE numeric time-series** (`ForcingTimeSeries` → `getArrayDouble`, a `;`-separated per-step
   biomass array), **not** a NetCDF file. The config's `species.file.spN = baltic_predator_biomass.nc`
   is **never read** by the background path (no `file`/`varname`/`mode`/`getFile` in `BackgroundSpecies`),
   so the migration must **materialize actual biomass numbers**, not pass the `.nc` pointer. (Optional
   companion `species.biomass.nsteps.year.spN`, default 1.)
3. **`species.beta.spN`** — absent but **optional** (default 1.0); emitting is harmless, not load-critical.
4. The existing `nclass`/`age`/`length`/`trophic.level`/`size.proportion`/`length2weight` are already
   present and correct. **The TL comma (`4.5, 4.8`) is NOT a problem** — Java's `Separator.guess` returns
   the first separator present (`,`) → 2 floats → passes the nclass-consistency check. No normalization
   needed.

**Layer 2 — the predation-accessibility matrix (the hard blocker):** `data/baltic/predation-accessibility.csv`
has **no GreySeal/Cormorant** predator columns or prey rows. 4.4.1 iterates background species as predators
(`getPredatorIndex = focal + bkg`) and dies at year 0: *"No accessibility found for predator GreySeal"*
(the same 4.3.3 blocker, unchanged in 4.4.1). The jar reports the missing **name**, not the **values** —
so the accessibility values must be **authored** (a source-data task, §3.2), not discovered by iteration.

## 3. Approach — two parts (a write-path migration + a source-data edit)

### 3.1 Migration keys — `osmose/config/aliases.py`
Add `_emit_background_species_keys(cfg)`, called from the `>=4.4.0` branch of `to_target_keys` (additive,
inert on 4.3.3; operates on the copied result dict; `setdefault` only — never overwrite an author value).
For each `species.type.spN == "background"` (exact match, not a prefix):
- **`species.multiplier.spN` = `"1"`** (scalar; biomass × 1 = as-is). No per-class form.
- **`species.biomass.spN`** = an **inline `;`-separated numeric biomass time-series**, materialized by
  reading `baltic_predator_biomass.nc` (the species' variable → domain-total biomass per step → the
  per-step array), plus **`species.biomass.nsteps.year.spN`** = the NetCDF's steps/year. Use the documented
  standing biomass (~4500 t seal / ~500 t cormorant, per the config comments) as the sanity/fallback if the
  NetCDF read is unavailable. **One-line jar probe first** to confirm whether the inline array is *total*
  biomass (then split by `size.proportion`) or already per-class — the spec assumes total; verify before
  authoring. This is a **distinct helper** from `_emit_resource_biomass_forcing`; do **not** emit
  `species.biomass.{mode,file,varname}.spN` for background (those are the `type=resource` path, ignored here).
- **`species.beta.spN` = `"1"`** (optional; default is 1.0 — emit for clarity).
- **Preserve** the existing `nclass`/`age`/`length`/`trophic.level`/`size.proportion`/`length2weight`
  verbatim. **No separator rewrite** (the comma TL parses fine — §2).

### 3.2 Background-predator accessibility — authored into the STAGED 4.4.x matrix (source untouched)
4.4.1 iterates GreySeal/Cormorant as predators and crashes without their accessibility entries, so they
must be added to `predation-accessibility.csv` as predator **columns** (and prey **rows**), with
**authored** values derived from the existing diet intent in `baltic_param-background.csv` (GreySeal →
herring/sprat/cod/flounder/pikeperch; Cormorant → perch/herring/sprat/young cod) and their size-ratio
windows (`predation.predPrey.sizeRatio.{max,min}.sp14/15`); as prey rows their accessibility to other
predators is ~0 (apex predators). This is **domain-authored, NOT iterative emit** — an all-zero matrix
would load but the predators would eat nothing (the §5 positive check guards this).

**Crucial placement decision:** `predation-accessibility.csv` is a **shared source file the Python engine
also reads**, and Baltic currently runs on the Python engine *without* background columns in it — so
editing the source could change Python-engine Baltic results. To honour the "no Python-engine change"
constraint, the augmentation is applied **only to the staged 4.4.x copy** (the staging step / smoke harness
rewrites the copied `predation-accessibility.csv` after `write_temp_config`'s `copytree`), leaving
`data/baltic/predation-accessibility.csv` (the canonical source the Python engine reads) **untouched**.
The authored values live in a small staging helper (e.g. `_augment_accessibility_for_440(stage_dir)` in the
smoke harness / a 4.4.x-staging utility), not in the source data. (Moving them into the canonical source +
re-validating the Python engine is a sub-project-C concern.) If 4.4.1 also needs the background species in
the catchability/discards matrices, augment those in the staged copy analogously.

## 4. Iterative jar-as-oracle — BOUNDED verification, not discovery

The init keys are already known from the bytecode (`multiplier`, `biomass`, `biomass.nsteps.year`) and the
matrix values are **pre-authored** (§3.2), so the loop is *verification*, not a fishing expedition: stage
at 4.4.1 → run the 4.4.1 jar 3 years → if a `severe`/consistency error still surfaces, add the specific
emit/value → repeat. **Bounded acceptance:** a clean 3-year run with all focal species non-zero AND the
background predators feeding (§5). Each addition is an explicit, commented emit/value — no silent guesses.

## 5. Validation

- **Unit (aliases):** `to_target_keys(baltic_cfg, "4.4.1")` for a `type=background` species emits
  `species.multiplier.spN` (scalar `"1"`), `species.biomass.spN` (an inline numeric array), and
  `species.biomass.nsteps.year.spN`; **does NOT** emit `species.biomass.{file,varname,mode}.spN`; preserves
  the existing `nclass`/`age`/`length`/`trophic.level` values verbatim; emits **nothing** on the 4.3.3 path;
  and operates on a copy (the source dict is unchanged).
- **Matrix (data):** assert `data/baltic/predation-accessibility.csv` has GreySeal + Cormorant predator
  columns, each with ≥1 non-zero focal-prey accessibility.
- **End-to-end `scripts/baltic_440_smoke.py`** (reuses `cross_engine_parity_440.py`'s staging): stage Baltic
  at 4.4.1 → run the 4.4.1 jar **3 years** → assert **exit 0**, output CSVs produced, **no focal species
  collapsed to zero**, AND — the **positive functional check** — **GreySeal/Cormorant appear in the diet
  output with non-zero predation on ≥1 focal prey** (or focal biomass differs measurably from an
  `nbackground=0` control). The positive check is essential: it guards against the empty-matrix false-pass
  (exit 0 + no collapse, but predators eating nothing). This is the acceptance gate for "loads + runs cleanly."
- **No parity claim** — a *loadability + functioning-food-web* port, not a calibrated Java≈Python match
  (Baltic is Python-calibrated + Python-only by design).
- **No Python-engine change** — the migration fires only on the 4.4.x *write* path, and the
  accessibility augmentation is applied only to the **staged 4.4.x copy**, so the canonical
  `data/baltic/*` source (incl. `predation-accessibility.csv`) the Python engine reads is **untouched**;
  the 4.3.3 default path is unchanged. A test asserts the source matrix is byte-identical after staging.
  Existing alias/migration/Python-engine tests stay green.

## 6. Edge cases

- A `type=background` species that already has `species.multiplier`/`biomass`/`beta` (author-provided) →
  left as-is (`setdefault`).
- **`species.biomass.spN` is required for EVERY background species** (it's the main case, not an edge): the
  4.4.x reader takes an inline numeric array regardless of any `.nc`, so the migration always materializes
  it. If the NetCDF read fails, fall back to the documented constant standing biomass.
- `nclass` vs array-length mismatch in the source config (author error) → surfaced by the jar's
  consistency check; the migration does not fabricate/trim per-class values.
- Background species missing from the catchability/discards matrices (if 4.4.1 requires them there too) →
  staged-copy augmentation analogous to the accessibility matrix (§3.2).

## 7. Future work — sub-project C (deferred, separate cycle)

"Standardise the Python setup to OSMOSE 4.4.x" — a distinct, larger cutover to brainstorm separately, with
the user-confirmed scope: (a) flip the default write-target 4.3.3 → 4.4.x; (b) migrate bundled config
masters to native 4.4.x; (c) make the Python engine read 4.4.x semantics natively (not only on write);
(d) UI 4.4.1 engine + version-aware `java_engine_block_reason` + full cross-engine re-validation. C
depends on this sub-project A (and the BoB 365-step-forcing fix) so every config loads on 4.4.x first.

## 8. Out of scope (this spec)

- Sub-project C above (the cutover) and the BoB 365-step blocker.
- Java≈Python parity validation for Baltic (loadability + non-collapse only).
- Any change to the Python engine, the bundled config sources, or the 4.3.3 default path.
