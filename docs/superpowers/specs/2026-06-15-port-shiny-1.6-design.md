# Port to shiny 1.6.3 everywhere — Design

**Date:** 2026-06-15
**Status:** approved (design), pending spec review

## Goal

Promote shiny **1.6.3** to the official, supported version of the OSMOSE web app across every environment (pyproject pins, dev `.venv`, CI, and the production deployment), lifting the long-standing `shiny<1.6` cap. Reconcile the dependencies that drifted in the deployment environment so all environments run a consistent, tested set.

## Background / why this is low-risk

The project pins `shiny>=1.3.0,<1.6` with a comment warning that 1.6 "compiles the custom theme via libsass" and "introduces API changes the UI isn't ported to yet." Empirical scoping on 2026-06-15 contradicts the "not ported" worry — the app is **already 1.6-compatible**:

- **Full non-e2e suite under shiny 1.6.3:** 3262 passed; the only 15 failures are environmental, not shiny: `cma 3.2.2` (vs `4.4.2`) API change in the CMA-ES runner, and copernicus `.env`-cred tests. **Zero shiny/UI failures.**
- **Full e2e suite under shiny 1.6.3 (theme, deck.gl maps, scenario diff, sensitivity, live movement, docs, feedback, map viewer, spatial results):** **50/50 passed.**
- The production deployment is **already running shiny 1.6.3** and serves correctly (the recent UI breakage was a stale-process/asset-desync issue, not the shiny version).

So this is **not** a UI-API migration; it is a **version-promotion + dependency-reconciliation** task. We deliberately take the minimal-alignment path (bump pins, declare the deps 1.6 actually needs, validate, roll out) rather than a proactive API rewrite (e.g. moving the `shinyswatch.theme.superhero` theme to `ui.Theme`). YAGNI: everything passes on 1.6.3 as-is.

## Scope

In scope ("everywhere"):
1. `pyproject.toml` dependency pins + comment.
2. Dev `.venv` reinstall.
3. CI (no workflow change needed; behavior follows the pins).
4. Production deployment: the shared micromamba `shiny` env (decision: keep shared, fix its drifted deps) + service restart.
5. Docs: pin comment, `CHANGELOG.md`, `DEPLOY.md`.

Out of scope:
- Proactive shiny-1.6 API adoption (`ui.Theme`, busy-indicator API, etc.) — not needed; tests pass.
- Isolating osmose into a dedicated deployment venv — the user chose to keep the shared env and fix its deps.
- The copernicus `.env`-cred test failures — those are a test-environment artifact (no creds in the shared env), not a shiny or dependency issue; they pass in CI / `.venv` where the test guards apply.

## Dependency changes (`pyproject.toml`)

1. **shiny:** `"shiny>=1.3.0,<1.6"` → **`"shiny>=1.6.3,<1.7"`**. Replace the multi-line "cap below 1.6" comment with a one-line note that 1.6.x is the supported baseline (theme compiled via libsass, declared below).
2. **libsass:** add **`"libsass>=0.23"`** (shiny 1.6 compiles the shinyswatch theme via libsass at app import; currently undeclared and only present in the deploy env by chance — a clean `pip install` of the project must pull it).
3. **cma:** add **`"cma>=4.0"`** as an explicit dependency. `osmose/calibration/cmaes_runner.py` imports `cma` directly but it is currently only pulled transitively via `pymoo`, so the version is unpinned and drifts (deploy env has 3.2.2, which breaks `cma.CMAEvolutionStrategy(...)`; `.venv` has 4.4.2, which works). Floor at 4.0 to guarantee the working API.
4. **shiny_deckgl:** currently `@v1.6.1`; the working deployment runs `1.9.2`. Validation step decides: if a clean install with `@v1.6.1` + shiny 1.6.3 passes the deck.gl e2e tests, leave it; otherwise bump the pin to the deployment-proven tag (`@v1.9.2`, to be confirmed it exists). The chosen tag must be recorded in the plan.
5. Leave `shinyswatch>=0.7.0`, `shinywidgets>=0.3`, `pyvis @v4.2` floors unchanged unless validation shows a concrete break.

## Validation (the gate)

All validation runs against a **clean venv built from the new pins** (Python 3.12), NOT the drifted shared micromamba env — so the `cma`/creds noise that polluted the scoping run cannot mask a real regression:

1. Build a fresh venv: `python3.12 -m venv` then `pip install -e ".[dev]"` (now resolves shiny 1.6.x + libsass + cma 4.x).
2. Confirm resolved versions: shiny in `[1.6.3, 1.7)`, libsass present, cma `>=4.0`.
3. **Full non-e2e suite green** (`pytest -m 'not e2e' -n auto`). Expect the 15 environmental failures from the scoping run to be GONE (clean install gets cma 4.x; cred tests are guarded).
4. **Full e2e suite green** (`pytest tests/test_e2e_*.py -m e2e`).
5. **ruff check + format --check** clean on `osmose/ ui/ tests/`.
6. **pyright** clean for **both** 3.12 and 3.13 (`--pythonversion`), matching CI.

A regression in any step blocks the port; if it is a real shiny-1.6 incompatibility (none found in scoping), it is fixed as part of this work.

## Rollout ("everywhere")

1. **`.venv`** (dev): `pip install -e ".[dev]"` to move it to 1.6.3 (or rebuild). This IS the validation venv from the gate.
2. **CI**: no workflow edit required — `pip install -e ".[dev]"` now pulls shiny 1.6.x + libsass + cma 4.x automatically. CI must be green on the branch (lint, type-check 3.12/3.13, test 3.12/3.13). This is the authoritative "clean install" signal.
3. **Production deployment** (shared micromamba `shiny` env):
   - `pip install` the corrected deps into `/opt/micromamba/envs/shiny`: upgrade `cma` 3.2.2 → 4.x (fixes prod CMA-ES calibration), ensure `libsass` present (it is), and align `shiny_deckgl` to the chosen tag if bumped.
   - `sudo systemctl restart osmose-shiny.service` (requires sudo; drops live sessions).
   - **Accepted risk:** the micromamba env is shared with telemac-viewer + aquabc; upgrading `cma` there could affect them. The user accepted this; the plan should still sanity-check those services come back up after the change.

## Testing

- The existing test + e2e suites ARE the regression net (proven to exercise the full UI under 1.6.3).
- No new tests are required for a version bump, EXCEPT: optionally add a lightweight guard that asserts the resolved `shiny` major/minor is within the supported range, to catch silent drift (the original problem the `<1.6` cap was guarding against). Decided in the plan; low priority.

## Risks & mitigations

- **shiny_deckgl/shiny 1.6.3 incompatibility at the pinned tag** → caught by the deck.gl e2e tests in the validation gate; mitigated by bumping to the deploy-proven tag.
- **Shared-env mutation breaks telemac/aquabc** → accepted by the user; mitigate by checking those services post-change and keeping the change to `cma` (+ deckgl) minimal.
- **Clean-install reveals a real 1.6 break the drifted env masked** → unlikely (scoping covered UI + non-UI), but the gate runs a clean install specifically to surface it before rollout.
- **Recurrence of version drift** → mitigated by declaring `libsass` and `cma` explicitly and the `DEPLOY.md` restart-after-pull note.
