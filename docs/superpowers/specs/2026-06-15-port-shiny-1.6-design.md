# Port to shiny 1.6.3 everywhere — Design

**Date:** 2026-06-15
**Status:** approved (design); revised after round-1 adversarial spec review
**Prerequisite (DONE):** CI was red from undeclared transitive deps (copernicus `fastmcp`/`copernicusmarine`, feedback `httpx`); fixed first as a separate change (commits `6fa0769`, `003336c`) — CI is green on master before this port begins.
**Prerequisite (DONE):** `razinkele/shiny_deckgl` tag **`v1.9.2`** now exists on GitHub (reconstructed from the deployed build as `main` + a clean 8-file delta; commit `c47b330`) and is pip-resolvable.

## Goal

Promote shiny **1.6.3** to the official, supported version of the OSMOSE web app across every environment (pyproject pins, dev `.venv`, CI incl. the docker leg, and the production deployment), lifting the `shiny<1.6` cap. Reconcile the dependencies that drifted in the deployment environment so all environments run one consistent, tested set.

## Background / why this is low-risk

The project pinned `shiny>=1.3.0,<1.6`, with a comment claiming 1.6 "compiles the custom theme via libsass" and "introduces API changes the UI isn't ported to yet." Scoping on 2026-06-15 (run in the deploy env, which is shiny 1.6.3; the authoritative figure is the clean-venv gate below) found the app is **already 1.6-compatible**: the full e2e suite (theme, deck.gl maps, scenario diff, sensitivity, live movement, docs, feedback) is **50/50** under 1.6.3, and the non-e2e suite's only failures were environmental (`cma 3.2.2` numpy-2 break; copernicus cred tests), not shiny. The production deployment already runs 1.6.3.

The round-1 review corrected two beliefs in the original draft:
- **libsass is NOT a shiny-1.6 requirement.** shinyswatch serves its **precompiled** superhero CSS only when its bundled Bootstrap version matches the Bootstrap the installed shiny resolves (`shinyswatch._can_use_precompiled`, given no theme customizations — osmose uses `theme.superhero` with no `add_rules`/`add_defaults`). shiny 1.6.3 bumped Bootstrap to **5.3.8**; shinyswatch <=0.10 bundle **5.3.1** (mismatch -> sass compile -> libsass needed), shinyswatch **0.11.0 bundles 5.3.8** (match -> precompiled, no sass). So the real fix is **bumping shinyswatch to re-align Bootstrap with shiny 1.6.3**, not declaring libsass. (The deploy env pairs shinyswatch 0.9.0's 5.3.1 with shiny 1.6.3's 5.3.8 -> mismatch -> which is why libsass is load-bearing *there* today.)
- **The `cma` break is a NumPy-2 incompatibility** in `cma` <=3.3.0 (uses numpy-2-removed APIs, e.g. `np.Inf` — the actual error from deploy's cma 3.2.2 under numpy 2.x), fixed in 3.4.0 — not a 3.x<->4.x API change.

So this is a **version-promotion + dependency-reconciliation** task, not a UI-API migration. We take the minimal-alignment path (bump pins, validate on a clean install, roll out) rather than a proactive API rewrite (e.g. moving to `ui.Theme`). YAGNI.

## Dependency changes (`pyproject.toml`)

1. **shiny:** `"shiny>=1.3.0,<1.6"` -> **`"shiny>=1.6.3,<1.7"`**. Replace the "cap below 1.6" comment with a one-line note that 1.6.x is the supported baseline.
2. **shinyswatch:** `"shinyswatch>=0.7.0"` -> **`"shinyswatch>=0.11"`** — 0.11.0 is the first shinyswatch that bundles Bootstrap 5.3.8, matching shiny 1.6.3, so the precompiled-CSS theme path is used and no sass compiler is needed at app import (older shinyswatch bundles 5.3.1, mismatches 1.6.3, and falls back to a libsass compile). Do NOT add a libsass dependency (no custom sass in the app).
3. **shinywidgets:** `"shinywidgets>=0.3"` -> **`"shinywidgets>=0.7"`** — raise the floor above the unrealistically-low 0.3 (deploy runs 0.7.2, `.venv` 0.7.1). This is a floor, NOT a lock: a clean install floats to the current 0.8.x, which the gate validates. (Same floor-floats behaviour applies to `cma>=4.0` and `shinyswatch>=0.11`; the clean-venv gate is the source of truth for the exact resolved set.)
4. **cma:** add **`"cma>=4.0"`** as an explicit dependency. `osmose/calibration/cmaes_runner.py` imports `cma` directly but it is only pulled transitively via `pymoo`, so its version drifts (deploy 3.2.2 is NumPy-2-incompatible and breaks `cma.CMAEvolutionStrategy`; `.venv` 4.4.2 works). Comment: floor at 4.0 (current major, validated; cma <=3.3.0 uses numpy-2-removed APIs like `np.Inf` and breaks `cma.CMAEvolutionStrategy` under numpy>=2, fixed in 3.4.0).
5. **shiny_deckgl:** `@v1.6.1` -> **`@v1.9.2`** (`git+https://github.com/razinkele/shiny_deckgl.git@v1.9.2`). This matches production and the `layer_legend_widget` code path the UI's `hasattr` branch targets; pinning 1.6.1 would make dev/CI test the *opposite* legend API from prod. The tag now exists (prerequisite above).
6. Leave `pyvis @v4.2` unchanged.

## Validation (the gate)

All validation runs against a **clean venv built from the new pins** (Python 3.12), NOT the drifted shared/deploy env — so `cma`/cred noise cannot mask a real regression:

1. `python3.12 -m venv` then `pip install -e ".[dev]"` (resolves shiny 1.6.x, shinyswatch >=0.11, shinywidgets >=0.7, cma >=4.0, shiny_deckgl 1.9.2).
2. Confirm resolved versions in range; confirm the theme renders without libsass installed (precompiled path).
3. `pytest --collect-only -m 'not e2e'` clean (0 collection errors) — the fast guard the round-1 CI-red work taught us to run.
4. **Full non-e2e suite green** (`pytest -n auto --cov=osmose --cov-fail-under=90`). The clean install gets cma 4.x and the copernicus/httpx fixes are already on master, so it must be deterministically green.
5. **Full e2e suite green** (`pytest tests/test_e2e_*.py -m e2e`) — the real theme/deck.gl/legend check under shiny 1.6.3 + shiny_deckgl 1.9.2.
6. **ruff check + format --check** clean on `osmose/ ui/ tests/`.
7. **pyright** re-run against the 1.6.3 venv for **both** 3.12 and 3.13 (`--pythonversion`, matching CI's per-leg flag); any new 1.6-stub-driven errors are fixed as part of this work (not assumed clean).
8. **Docker leg:** `docker build` (the CI `docker` job runs `pip install .`); confirm it still builds on the new pins (the runtime now resolves shiny 1.6.x + shiny_deckgl 1.9.2; shinyswatch >=0.11 means no libsass needed at `shiny run`).

CI on the branch (lint, type-check 3.12/3.13, test 3.12/3.13, docker) is the authoritative clean-install signal and must be green.

## Rollout ("everywhere")

1. **`.venv`** (dev): `pip install -e ".[dev]"` to move it to the new set (this IS the validation venv).
2. **CI**: no workflow edit required — `pip install -e ".[dev]"` / `pip install .` now resolve the new pins automatically; all six legs must be green.
3. **Production deployment** (shared micromamba `shiny` env at `/opt/micromamba/envs/shiny`):
   - The env is shared by ~11 shiny-server apps (AQUABC, telemac, telemac-viewer, marxan, shyfem, ...) — **none import `cma`/`pymoo`** (verified), so the `cma` upgrade is safe for co-tenants; the env is already on shiny 1.6.3.
   - **Targeted upgrades only**: `pip install --upgrade "cma>=4.0" "shinyswatch>=0.11" "shinywidgets>=0.7"` and reinstall `shiny_deckgl @v1.9.2` (prod already runs 1.9.2, so this just makes it the GitHub-tagged build). Do **NOT** `pip install -e .` of osmose into the shared env — osmose runs as a source copy, and a full install would churn shared transitive deps (the real co-tenant hazard).
   - `sudo systemctl restart osmose-shiny.service`; then sanity-check the co-tenant services still serve.
4. **`deploy.sh`**: its existing loop is **presence-only** (`if ! pip show "$pkg"`), so it installs a package only when ABSENT and CANNOT enforce a minimum version — adding bare names (`cma` etc.) would be a no-op since they are already present (the exact drift this is meant to prevent). Instead add an **unconditional version-aware upgrade**: `pip install --upgrade "cma>=4.0" "shinyswatch>=0.11" "shinywidgets>=0.7"` and reinstall `shiny_deckgl @v1.9.2`, followed by a **post-step version re-check** (`importlib.metadata.version`) that fails loudly if any is below floor. Update `DEPLOY.md` to state shiny 1.6.x is the supported line and list this upgrade command.

## Testing

- The existing test + e2e suites ARE the regression net (proven to exercise the full UI under 1.6.3 + deck.gl 1.9.2).
- No new functional tests are required for a version bump. Optionally add a lightweight guard asserting the resolved `shiny` minor is within `[1.6, 1.7)` to catch silent drift (the concern the old `<1.6` cap guarded); low priority, decided in the plan.

## Risks & mitigations

- **shiny_deckgl 1.9.2 legend path under shiny 1.6.3** -> covered by the deck.gl e2e tests in the gate (now testing the SAME `layer_legend_widget` path prod runs, eliminating the prior dev/prod divergence).
- **Shared-env mutation affects co-tenants** -> de-risked: no co-tenant uses `cma`; upgrades are targeted (cma/shinyswatch/shinywidgets/deckgl), not a broad reinstall; co-tenant services sanity-checked post-change.
- **Clean install surfaces a real 1.6 break the drifted env masked** -> the gate runs a clean install + collection check specifically to surface it before rollout; pyright re-run at 1.6.3.
- **Recurrence of version drift** -> mitigated by the explicit `cma`/`shinyswatch`/`shinywidgets` pins, the extended `deploy.sh`, and the `DEPLOY.md` restart-after-pull note.
