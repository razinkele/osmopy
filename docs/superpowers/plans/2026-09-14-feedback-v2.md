# Feedback v2 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let any user of the public Shiny app report a bug or request a feature in a few seconds, optionally leave an email for follow-up, and give the maintainer a triage surface that promotes a chosen item into a GitHub issue in one click.

**Architecture:** Three layers, each independently testable. (1) A hardened append-only JSONL store in `osmose/feedback.py`, with the optional email split into a **separate private side-store** so the record a maintainer copies to GitHub can never carry PII. (2) A modernised submit modal in the Shiny UI with client- and server-side validation and abuse controls sized for public exposure. (3) A **token-gated maintainer review page served as a plain Starlette route** — deliberately *not* a Shiny nav page, so the maintainer surface is not discoverable from the public app and reuses the auth that already exists and is tested. Promotion to GitHub is a prefilled `issues/new` URL, so no API token, no bot account, and no new secret is introduced anywhere.

**Tech Stack:** Python 3.12, Shiny for Python, Starlette (already the ASGI layer under Shiny), Bootstrap 5 (already vendored for the existing modals), pytest.

**Spec:** This document, §Design Decisions. No separate spec file — the decisions were settled interactively and are recorded below with their rationale so the plan is self-contained.

---

## Design Decisions

These were chosen deliberately; do not silently revise them while implementing.

| # | Decision | Why |
|---|---|---|
| D1 | Feedback stays in a **local JSONL store**; no automatic GitHub issue creation. | `github.com/razinkele/osmopy` is **PUBLIC** with issues enabled. Auto-creating issues from a public app hands anyone a spam channel into the tracker. A maintainer gate is the protection. |
| D2 | Email is stored in a **separate private side-store**, never in the main record. | The record is designed to be copied into a public GitHub issue. Keeping email out of it structurally prevents a PII leak, rather than relying on whoever does the copying to remember. |
| D3 | Review UI is a **token-gated Starlette route**, not a Shiny page. | Reuses `check_feedback_token`, already tested including the non-ASCII crash case. Keeps the maintainer surface off the public app's nav. |
| D4 | GitHub promotion is a **prefilled `issues/new` URL**. | No API token, no bot identity, no secret to rotate or leak. The maintainer's existing browser session authenticates them, and they see the issue before it is filed. |
| D5 | Abuse controls sized for the **public internet**. | The app is publicly reachable. The current implementation has no rate limit, no size cap on `contact`, and unbounded store growth. |
| D6 | Backwards compatible with existing records. | `data/feedback/feedback.jsonl` may already hold records written by v1. The reader must not break on them. |

**What this plan explicitly does NOT do:** create issues via the GitHub API, send email, add a captcha service, or introduce any third-party dependency. Each was considered and rejected as more surface than the problem warrants.

### Task 2: Split email into a private side-store

```python
CONTACTS_FILE = _PROJECT_ROOT / "data" / "feedback" / "contacts.jsonl"
_CONTACTS_ENV = "OSMOSE_CONTACTS_FILE"


def _resolve_contacts(path: Path | None) -> Path:
    if path is not None:
        return Path(path)
    env = os.environ.get(_CONTACTS_ENV)
    return Path(env) if env else CONTACTS_FILE


def save_contact(feedback_id: str, email: str, *, path: Path | None = None) -> None:
    """Store an address OUT OF BAND, keyed by feedback id. Never goes in the main record."""
    email = (email or "").strip()[:MAX_CONTACT]
    if not email:
        return
    p = _resolve_contacts(path)
    p.parent.mkdir(parents=True, exist_ok=True)
    with open(p, "a", encoding="utf-8") as f:
        f.write(json.dumps({"id": feedback_id, "email": email}) + "\n")


def lookup_contact(feedback_id: str, *, path: Path | None = None) -> str | None:
    p = _resolve_contacts(path)
    if not p.is_file():
        return None
    for raw in p.read_text(encoding="utf-8").splitlines():
        try:
            rec = json.loads(raw)
        except Exception:  # noqa: BLE001
            continue
        if rec.get("id") == feedback_id:
            return rec.get("email")
    return None
```

In `build_feedback_record`, replace the `contact` field with:

```python
        "has_contact": bool((contact or "").strip()),
```

**D6 compatibility:** `read_feedback` must tolerate v1 records that still carry a literal `contact` key. Add, in the read loop, after `json.loads`:

```python
        rec.setdefault("has_contact", bool(rec.pop("contact", "")))
```

so old records are normalised on read and their address is dropped from what callers see.

```python
"""In-process rate limiter for feedback submission (public deployment, D5).

Deliberately in-memory: a single-worker Shiny deploy is the documented target, and a
persistent limiter would be a second consistency problem for no benefit. If the app is ever
run multi-worker, this becomes per-worker and the cap must be divided accordingly — stated
here so the limitation is visible rather than discovered.
"""

from __future__ import annotations

from collections import defaultdict


class RateLimiter:
    def __init__(self, max_per_window: int, window_s: int) -> None:
        self.max_per_window = max_per_window
        self.window_s = window_s
        self._hits: dict[str, list[float]] = defaultdict(list)

    def allow(self, key: str, now: float) -> bool:
        cutoff = now - self.window_s
        if len(self._hits) > 1000:  # prune globally before it can grow without bound
            for k in [k for k, v in self._hits.items() if not v or v[-1] < cutoff]:
                del self._hits[k]
        hits = [t for t in self._hits[key] if t >= cutoff]
        if len(hits) >= self.max_per_window:
            self._hits[key] = hits
            return False
        hits.append(now)
        self._hits[key] = hits
        return True
```

```python
from urllib.parse import urlencode

_LABEL = {"bug": "bug", "suggestion": "enhancement", "other": "question"}


def github_issue_url(record: dict, repo_url: str) -> str:
    """Prefilled issues/new link. NEVER includes contact details (D2) — see the test."""
    kind = record.get("type", "other")
    first = (record.get("message") or "").strip().splitlines()[0][:60]
    body = (
        f"{record.get('message', '')}\n\n---\n"
        f"- app version: `{record.get('version', '?')}`\n"
        f"- tab: `{record.get('nav_tab', '?')}`\n"
        f"- feedback id: `{record.get('id', '?')}`\n"
        f"- reporter left contact details: {'yes' if record.get('has_contact') else 'no'}\n"
    )
    q = urlencode({"title": f"[{kind}] {first}", "body": body, "labels": _LABEL.get(kind, "question")})
    return f"{repo_url.rstrip('/')}/issues/new?{q}"
```

## Self-Review

**Spec coverage.** Bug + feature request (Task 4 radio options), optional email (Tasks 2, 4), integration with the development process (Tasks 5, 6 — triage then one-click issue), public-internet hardening (Tasks 1, 3, 4), PII safety (Tasks 2, 5, 6, 7).

**Placeholder scan.** Every code step carries real code. Task 5 Step 1 and Task 6 Step 3 show `...` only inside test bodies whose *assertions* are fully specified — the fixture setup is the implementer's, the contract is not.

**Type consistency.** `build_feedback_record` gains `honeypot` (Task 1) before Task 4 calls it with that name. `has_contact` is introduced in Task 2 and consumed in Tasks 5 and 6. `RateLimiter.allow(key, now)` is defined in Task 3 and called with both arguments in Task 4.

**Known residual risks, recorded rather than hidden.**
1. The rate limiter is per-process; a multi-worker deploy divides the effective cap. Documented in the module docstring.
2. `_client_key` depends on Shiny exposing `session.http_conn.client.host`; behind a reverse proxy this may be the proxy's address. **Task 4 must verify this on the real deployment** and fall back to `X-Forwarded-For` only if the proxy is trusted — an untrusted `X-Forwarded-For` is attacker-controlled and would make the limiter useless.
3. A honeypot stops naive bots, not a targeted attacker. If abuse becomes real, the next step is a proof-of-work or captcha — deliberately out of scope until there is evidence it is needed.
